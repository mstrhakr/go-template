Docker Compose

cp .env.example .env
docker compose up --build -d
docker compose logs -f
curl http://localhost:8080/healthz
docker compose down

Compose reads .env for the host port and log level. The multistage image contains a static binary and CA certificates, runs as UID/GID 65532, and provides a built-in health check. Compose uses a read-only filesystem, drops capabilities, and prevents privilege escalation. No secrets, source files, shell, or docs are included in the runtime image.

The default host binding is 127.0.0.1. For remote use, put a TLS reverse proxy in front of it. If the proxy is another container, connect it to the same Docker network and use app:8080 instead of loopback. Do not expose future administrative routes without authentication.

Container registry (off by default)

After explicit setup, relevant passing protected-main CI triggers dev images. Only successful main push runs from this repository's CI are accepted, never PR runs or arbitrary artifacts. A read-only job builds/scans/smoke-tests; a separate job loads and pushes the image without executing it; a separate OIDC job attests its digest. Initial images are Linux x64. No Docker socket is exposed to the scanner; its image is digest-pinned.

Registry names are lowercase. Dev uses dev and sha-FULL_COMMIT_SHA; beta/RC use their exact version tags plus beta/rc; only normal moves latest. Do not deliberately overwrite version/SHA tags. Roll back by an exact version or digest only when config/data remain compatible. GHCR package visibility is separate from repository visibility; check package access explicitly.

GitHub setup for each repository

Template-created repos do not inherit live settings. Authenticate GitHub CLI outside chat, review this public-repo setup, then explicitly apply it:

node scripts/setup-github.mjs --repo OWNER/PROJECT
node scripts/setup-github.mjs --repo OWNER/PROJECT --apply
# Only when publication is authorized:
node scripts/setup-github.mjs --repo OWNER/PROJECT --apply --enable-publishing

The script never changes visibility or buys plan features. It requires admin access, a public repo and main as the default branch. It enables Issues, private security reporting, secret scanning/push protection, Dependabot alerts/fixes, squash-only PRs, the required CI gate, immutable version tags, read-only Actions defaults and SHA-pinned allowlisted Actions. It disables Wiki, Discussions, dependency auto-merge and routine ruleset bypass.

Setup preserves the repository's existing template status; it does not mark new projects as templates. Set that GitHub setting separately if you intend to create another reusable template.

The release environment requires the applying maintainer's approval and protected-branch deployment. Self-review remains allowed for a solo maintainer; this is an intentional approval pause, not two-person security. GitHub combines bot-PR creation and approval in one Actions settings switch; the script enables it so Release Please can create PRs, not to authorize automatic approvals.

Without --enable-publishing, release/container variables are false. With it, RELEASES_ENABLED, PUBLISH_CONTAINER, and the verified-setup acknowledgement RELEASE_APPROVAL_CONFIGURED are true. Keep the environment protected; that acknowledgement is not itself enforcement. Docs publication remains separately off. Apply local changes through a feature branch/PR; do not bypass the new main rule to bootstrap them.

Versions and release channels

Initial normal version: v0.1.0. Before v1, feat/fix increment patch; breaking changes increment minor. Docs/test/chore-only work does not ordinarily release the app. Entering v1 requires an explicit policy/config change.

Release Please opens/updates version/changelog PRs. Its built-in token does not automatically trigger PR workflows, so a separate scoped dispatch job starts CI on the generated branch. Merging the release PR creates a draft release; full validation, packaging, checksums, attestations and release-environment approval precede publication. A failed stage leaves a visible failed run/draft, not an implied successful release. Do not manually publish that draft to skip gates.

For beta/RC, run Releases (opt-in) manually on main, selecting channel, exact tag (for example v0.2.0-beta.1 or v0.2.0-rc.1), and full 40-character main-history commit SHA. Branch names are rejected. RC means intended final scope; new features return to beta. These prereleases are optional for small fixes. Final release source/build changes require validation, not blind promotion of a moving candidate alias. Release numbering is independent from Go toolchain versions.

Security boundaries apply at every stage. Native CI covers declared OS/architecture targets; local cross-builds do not establish native Windows/macOS support. No desktop framework is included.

Verify downloads and images

GoReleaser produces Linux/Windows x64 and macOS x64/ARM64 downloads, checksums and embedded version/revision metadata. Use server -version locally. Verify checksums and provenance with the repository/workflow you expect:

sha256sum --check checksums.txt
gh attestation verify FILE --repo OWNER/PROJECT --signer-workflow OWNER/PROJECT/.github/workflows/publish.yml
gh attestation verify oci://ghcr.io/owner/project@sha256:DIGEST --repo OWNER/PROJECT --signer-workflow OWNER/PROJECT/.github/workflows/image.yml

For a manually selected source revision, the triggering workflow revision may differ from packaged source. Verify the additional signed source-revision receipt and inspect its repository/revision/tag/run against your expectations:

gh attestation verify FILE --repo OWNER/PROJECT --predicate-type https://github.com/mstrhakr/go-template/source-revision/v1 --format json

The predicate URI identifies this schema, not a required upstream signer. Verify your own repository/workflow identity. Attestations are origin evidence, not proof that upstream code or an authorized workflow is harmless. Publication and consumer-side verification must be exercised before claiming end-to-end verification; local snapshot builds alone do not provide that evidence.

Support, retention and recovery

Initially support the latest normal release; dev/beta/RC are test channels. Retain normal and prerelease versions. Target about 30 days of dev registry history with cautious manual cleanup; do not delete referenced release digests. CI reports/build handoff artifacts expire after seven days. No deletion bot is given broad package write access. For incidents, stop publishing, revoke affected access, review trusted source/workflows, rebuild, and restore deliberately.

GitHub Pages (off by default)

A private repository does not guarantee a private Pages site. Pages availability and private-site access controls depend on your GitHub plan. Treat publishing as public disclosure unless you have explicitly verified access controls. No repository visibility or Pages setting is changed automatically.

  1. Review the generated content and remove anything that must remain private.
  2. When ready, select GitHub Actions as the Pages source in repository settings.
  3. Set the Actions variable PUBLISH_DOCS to true.
  4. Run “Publish documentation (opt-in)” on the default branch and explicitly confirm publication. Optionally require approval on the github-pages environment.

The workflow derives the base URL from GitHub Pages, so project paths and custom domains do not require hardcoded repository names. Preview locally with make docs-serve while publishing remains disabled. Changing either opt-in variable back to false prevents future runs, but does not delete already published sites, packages, or artifacts.

Contracts stay excluded unless PUBLISH_CONTRACTS=true. Preview them locally with make docs-contracts before enabling that variable.
